## Resource and recovery model

Example policy defaults: shared request allowance 40 tool calls; instructor 20-call batch with up to two continuations; junior 20 calls per shared request; six delegations; read-only planning 24 calls; 500 model turns per attempt; 900,000 ms (15 min) attempt pause/delegation/continuation-approval limit; 3,600,000 ms (60 min) aggregate deadline that does not pause; 2,000 aggregate model calls; provider inactivity watchdog 60 sec (rearmed while streaming); command timeout 120 sec; $1/request and $5/day. Values are configurable, not fixed product maxima: schema permits tool max 300, turns 1,000, attempt max one hour, continuations max ten (`packages/teapilot/src/config.ts:71–75, 169–192`). Config precedence: `TEAPILOT_POLICY_FILE`, then policy/config files and packaged example (`packages/teapilot/src/config.ts:71–75, 169–192`). Junior call limits are also hardcoded as 20 in delegate profiles/fallback/progress displays, unlike configurable allowance (`delegate.ts:12, 98–99, 135–136, 186`; `packages/teapilot/src/agents/allowance.ts:73–74`), an inconsistency to audit. Local API providers enforce zero dollar cost, so dollar caps alone do not contain resource use (`packages/teapilot/src/config.ts:183–185`).

`packages/teapilot/src/host.ts:376–430, 450–480` coordinates tiers, accounting and recovery; instructor is the main model and nested juniors run sequentially in the same request (`delegate.ts:18–23`). Delegates share workspace, budget, allowance and recovery; they are not filesystem/permission isolated and cannot recurse. Some allowance is reserved for a sibling and up to four finishing calls (`delegate.ts:14–23, 164–194`; `packages/teapilot/src/agents/allowance.ts:59–117`). A single request execution lock per state directory makes cooperative checkpoint/yield/fairness relevant; reflexive parallelism is not a safe assumption. Spend reservations fail closed on corrupt/unknown usage and retain max budget (`budget.ts:25–51, 62–123`).

Attempt `timeout` and `tool_limit` are terminal; other same-tier recovery decisions use a made-progress heuristic based on coder/file/shell or model turns, not verified task advancement (`packages/teapilot/src/host.ts:450–477`). Identical-result escalation warns and withdraws tools after a third repeat; web/search have narrower rules. Paging warns at four and pressures read-only synthesis at six (`packages/teapilot/src/routing/escalation.ts:136–170, 65–83`). Same failed result defaults to three, check-failures to two; ten consecutive tool failures warn and fifteen require approval, though other triggers can stop first (`run.ts:675–681`). Writes can reset some loop counters, and non-scratch edits clear bash counters; neither proves useful advancement (`packages/teapilot/src/routing/escalation.ts:123–134`). Provider watchdog is liveness, not usefulness (`providers.ts:220–229`); malformed/truncated calls are blocked (`providers.ts:279–296`). Juniors get a three-call warning; read-only/junior runs withdraw before exhaustion; general instructor continuation gate appears at exhaustion (`run.ts:568–575, 714–717`).

An optional task store (`TEAPILOT_TASK_STATE=on`) applies to eligible tool requests in scratch, default off (`packages/teapilot/src/config.ts:200`, `packages/teapilot/src/host.ts:386–394`, `task-defaults.test.ts:13–50`). Reopening a task preserves counters/deadline, but a new invocation gets a UUID and fresh allowance (`packages/teapilot/src/workspace/task.ts:229–239`, `packages/teapilot/src/host.ts:112–123`). Task ledger distinguishes model claims from host completion and records scoped receipts/epochs/uncertain incomplete effects; these are provenance, not semantic truth (`packages/teapilot/src/workspace/task.ts:281–282, 364–448`; `task.test.ts:517–534`). The check classifier is regex-based around words such as test/build/check (`packages/teapilot/src/routing/escalation.ts:17–18`, `run.ts:651–655`), not an acceptance oracle. Compaction keeps refs/current host scope and shares budget (`compaction.ts:12–15`, `run.ts:377–383, 435–461`).

## UI and important failure modes

Discord reports activity/recent operations/reasoning/elapsed time/step count with a five-second heartbeat and 1.5-second throttle; these are not verified progress (`run.ts:760–800`, `bridge.ts:354–405`, `render.ts:84–126`; event source: `packages/teapilot/src/integration/events.ts`). Details/Stop controls are requester/operator scoped (`bridge.ts:219–240, 336–343`; `gateway.ts:256–281`). Stop cancels current task execution but cannot undo side effects already made; pause should checkpoint at the next safe boundary. Operation deadlines and cancellation guards are needed so a stuck operation cannot indefinitely block controls. Continuation uniquely auto-approves after 45 seconds, unlike ordinary approvals; cancellation race guards exist (`discord-continuation.test.ts:106–260`). Interaction expiry around 15 minutes pauses live updates; Resume refreshes delivery, not task execution, and durability is optional (`packages/teapilot/src/discord/feed.ts:8–12`). A denied continuation can still produce `success:true` for partial synthesis (`run.test.ts:134–162`, `run.ts:839–842`): host success is not acceptance success.

## Design implications to evaluate

Separate (1) authorization/hard exposure envelope (permissions, hard configured budget/runtime, dangerous operations), (2) renewable bounded execution leases, and (3) evidence of task progress. A lease boundary should provide a review/checkpoint opportunity; it should not silently enlarge hard limits. At a safe tool-batch boundary, deterministic host logic can choose continue within authorized envelope, steer, ask, checkpoint/yield, or stop—no extra supervisor-model call required. Preserve cancellation and uncertainty about side effects as hard guardrails.

Use fresh relevant acceptance results as strongest evidence, then scoped inspected artifacts/diffs and milestone receipts; plans and explanations are weaker. Do not reward token volume, UI updates, file counts, scratch changes, timestamps, artifact existence, revisions, changed hashes, or mandatory bookkeeping loops. Do not require tests to pass at each lease: deliberate debugging/research and slow operations can be valid. Detect no-op/test churn worker-locally before task-global escalation; repeat signatures are inspection prompts, not universal stagnation proof. Warnings should state concrete evidence and uncertainty, never claim universal automatic detection.

Make up-front authorization preference explicit: default long-task behavior versus opt-in, soft configured ceilings versus hard ones, bounded uncertainty/grace, durable task state, and lock fairness are product decisions. If no preference exists, do not infer silence means unlimited continuation. At authorization, state hard ceiling and what renewals cost; within it, surface an early warning and defer steering to the next safe boundary. Keep a checkpoint capacity reserve for verification/reporting. Durable task state should carry lease ID, cumulative authorization/consumption, checkpoints, pending effects and amendments outside compacted context; restarting must reconcile uncertain effects, not blindly replay. Clearly label memory-only work versus resumable long tasks.
