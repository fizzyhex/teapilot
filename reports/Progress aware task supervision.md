# Let long-running agents checkpoint and continue

Teapilot should keep users informed by separating **progress warnings from resource limits**: a tool-count or time boundary should trigger a compact, evidence-based checkpoint and an authorized choice to continue, steer, pause, or stop—not automatically declare useful work a failure. Hard spend, safety, permission, and explicit cancellation limits must remain enforceable; progress signals must never expand them. The latest Discord Mario run shows why this distinction matters: it made real code and debugging changes, but spent later attempts repeating failed tests, exhausted attempt time/context, and finally claimed completion despite not publishing a working game. The practical direction is bounded, renewable execution leases with visible verified milestones, safe-boundary steering, and durable task state—not unlimited autonomy, a mandatory bookkeeping loop, or another model supervising every tool call.

## Mario made artifacts, but retries stopped making progress

The three logged requests provide a useful mixed case, not a clean success or a simple “agent got stuck” story. The first request created a level design, game code, and a generator before ending at its 20-call instructor batch limit. The second request had a junior blueprint and repeated task-state updates, then timed out even though its last view showed aggregate time and calls remaining. A continuation approval retained shared ceilings but did not prevent the current attempt’s own timeout. In the third request, an SDK import was fixed, but the game test still reported 0/48 actions completed, 48 skipped, zero passed and three failed; subsequent play attempts did not publish because the code and test result were unchanged. After the same failed result recurred, tools were withdrawn, context admission failed twice, and the final “built and ready” claim conflicted with the test and publication evidence. These details are from the targeted session transcript and outcomes log summarized in [`mario_case.md`](../research_notes/Progress%20aware%20task%20supervision/mario_case.md); relevant code paths include `packages/teapilot/src/agents/allowance.ts:118–143`, `packages/teapilot/src/agents/run.ts:574–575`, `packages/teapilot/src/agents/play.ts:297–320`, and `packages/teapilot/src/inference/providers.ts:248–265`.

The case suggests two distinct failures. **Renewing permission was not the same as renewing a viable attempt:** the continuation could preserve the aggregate envelope while an independent attempt timer still expired. And **successful tool execution was not successful task delivery:** telemetry said the play tool call succeeded, but that indicated tool execution, not publication or acceptance. Conversely, the first requests did make work that survived, so treating every limit or repeat as proof of stagnation would also be wrong. There are unresolved historical details: the exact running build and policy were not recovered; the cause of an empty projected step list is untraced; and actual user-visible delivery was not verified. Treat the event as a warning about current behavior, not a production-wide rate estimate.

## Keep hard ceilings separate from renewable work windows

The current checkout already has multiple limits: example settings include 40 shared tool calls, 20-call instructor batches, a 15-minute attempt limit, a 60-minute aggregate deadline, model-call ceilings, provider/command timeouts, and spend limits (`packages/teapilot/config/policy.example.json:10–25`; `packages/teapilot/src/agents/allowance.ts:9–16`; `packages/teapilot/src/agents/run.ts:348–361, 804–806`). They are configurable, not universal product maxima. Crucially, the 15-minute attempt limit, shared call allowance, and aggregate deadline are not interchangeable. Feedback should identify the earliest binding limit and show remaining attempt active time alongside aggregate time and calls. A continuation approval that does not extend the attempt’s time cannot rescue a task from that deadline; multiplying approval windows without stating the aggregate limit would instead create misleading expectations.

Model these controls explicitly as **an authorization envelope plus a renewable execution lease**. The envelope states what the user authorized and the hard boundaries that remain fixed: permissions, spend, maximum runtime or other configured exposure, and immediate safety/cancellation rules. A lease is a shorter work window that ends at a safe tool-batch boundary with a checkpoint and review opportunity. A lease boundary is not evidence of failure and does not grant extra authority. Renewal can continue only within the envelope; if that envelope is exhausted, stop or ask for a separately authorized amendment. At the outset, tell users whether their request is memory-only or durably resumable, what hard ceiling applies, and what happens when a lease ends. If Teapilot has no explicit long-task authorization, do not interpret silence as permission for indefinite execution.

At a checkpoint, deterministic host logic should choose among **continue within the authorized envelope, ask for steering, pause/yield, or stop** using the task’s current evidence and known limits. A compact policy is:

| Evidence/state | Response |
| --- | --- |
| Credible recent progress | Bounded automatic renewal inside the preauthorized envelope. |
| Uncertain, novel diagnostic work | Finite exploration grace, then review. |
| Repeated unchanged failure or no-op | Local contextual steer; checkpoint and ask if it persists. |
| Hard cap, cancellation, or unsafe action | Stop independently of progress. |
| Context cannot be admitted | Compact relevant state or start with fresh bounded context; never retry the identical oversized request. |

Warnings and review points inside the envelope are nonblocking; do not demand repeated permission at every checkpoint. Reserve enough capacity for a final relevant check, checkpoint, and honest report. Current recovery already distinguishes some terminal outcomes from retryable ones and has repeated-result escalation, but its general same-tier progress heuristic can rely on activity such as model turns rather than verified task advancement (`packages/teapilot/src/host.ts:450–480`; `packages/teapilot/src/routing/escalation.ts:136–170`). Task-store receipts and host completion provenance help trace events, but do not themselves prove semantic success (`packages/teapilot/src/workspace/task.ts:281–282, 364–448`).

## Warn about concrete evidence, not a guessed progress score

Surface warnings before a lease or resource boundary where practical, then defer steering to a safe point. A useful compact update is: **“still working on [milestone]. [Relevant result] hasn’t changed since [event]; next I’ll [bounded action]. The current window ends at [boundary]. continue, steer, or pause?”** When the agent is advancing, say what actually changed: a milestone passed, a relevant artifact was inspected, or a fresh diagnostic narrowed the cause. Avoid a percentage unless the task has a meaningful, externally grounded denominator. Provide sparse, contextual feedback from relevant tool results, not model-generated bookkeeping after every call.

Progress evidence has different strengths. A fresh acceptance check or externally observed result is strongest; an inspected, task-relevant diff or artifact and a new diagnostic can substantiate work in progress. A plan update or agent explanation is weaker and should not count as proof by itself. Conversely, **do not reward token volume, timestamps, file counts, scratch churn, task-state revisions, changed hashes, or repeated checks of unchanged code**. A repeat detector can identify a possible loop, but changed arguments can hide equivalent failures and identical actions can be legitimate polling or convergence. Use it to prompt inspection or an evidence-based warning, not to decide universally that work is useless. Do not demand a passing test at every window or claim each checkpoint is a verified milestone: a test can be unavailable, slow, or deliberately failing while the agent is debugging. Report the exact result and distinguish “tool ran,” “check passed,” “published,” and “task accepted.”

Teapilot’s Discord status currently reports activity, recent operations, elapsed time and step count; that helps show liveness but is not verified progress (`packages/teapilot/src/integration/events.ts` and Discord bridge/render paths summarized in [`current_harness.md`](../research_notes/Progress%20aware%20task%20supervision/current_harness.md)). A concise status card can instead show **current milestone**, **last verified advance**, **next review point**, and **known blocker/check result**. For Mario, for example: “sdk import fixed; controls test still failing (0/48 actions, 48 skipped); no app posted; next: fix controls, then rerun after a relevant edit.” Controls should stay small and intelligible: stop cancels execution now but cannot undo effects already made; pause checkpoints at the next safe boundary; steer at a safe boundary. Operation deadlines and cancellation guards should prevent a stuck operation from blocking these controls indefinitely. Continue only when authorization allows. Say “no verified change since the last check,” not “stuck,” unless the evidence supports that conclusion. If the Discord interaction expires, distinguish a delivery/update problem from a task that stopped; the feed can pause updates without pausing task execution, though durability is optional (`packages/teapilot/src/discord/feed.ts:8–12`).

## Borrow checkpoints and steering, not other systems’ claims

The strongest external patterns support this separation. Anthropic’s long-running scientific-computing example uses a scoped goal, explicit acceptance criteria, a persistent log of completed work and failed approaches, and an external reference/test oracle; it also reports a clunky but productive trajectory and limitations in test coverage. Its lesson is not “tests always tell the whole story,” but that recovery benefits from durable facts and known failed paths. ([Anthropic, “Long-running Claude for scientific computing”](https://www.anthropic.com/research/long-running-Claude)) OpenAI’s harness engineering and long-horizon Codex accounts describe milestone validation, decision/progress logs, recovery, and verification, while presenting company examples rather than independent evidence that any particular supervision policy works for all tasks. ([Harness engineering](https://openai.com/index/harness-engineering/); [Run long horizon tasks with Codex](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex))

For control and recovery, LangGraph documents persistent checkpoints and interrupts that expose a payload, wait, and resume at a defined boundary; OpenHands documents explicit pause/resume and goal-stop APIs. OpenCode’s runner distinguishes steering input at a provider-turn boundary from queued input that waits until idle. These are useful interface patterns, not evidence of reliable automatic stagnation detection. ([LangGraph checkpoints](https://docs.langchain.com/oss/python/langgraph/checkpointers); [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts); [OpenHands pause/resume](https://github.com/openhands/docs/blob/main/sdk/guides/convo-pause-and-resume.mdx); [OpenCode runner](https://github.com/anomalyco/opencode/blob/dev/packages/core/src/session/runner/llm.ts)) The reviewed public material establishes no generally reliable numerical threshold for stagnation, no universally safe lease length, and no validated precision/recall for detectors. Teapilot should therefore expose uncertainty and tune using its own labeled traces rather than inventing a magic call count or inactivity interval.

## Roll out with durable checkpoints and replayable evidence

First, make boundary semantics legible: distinguish attempt timeout, aggregate deadline, tool-call allowance, provider/context failure, explicit stop, and hard safety/spend stop in the status and final result. Fix the continuation/attempt-time mismatch before presenting “continue” as a fresh time window. Keep activity, partial output, successful acceptance checks, and completed delivery as separate statuses. Reconcile configurable junior limits with hardcoded 20-call displays/behavior noted in the current harness note; otherwise a progress card can report the wrong remaining allowance.

Next, persist a compact, versioned checkpoint outside the model context: goal and acceptance criteria; bounded hot working state; recent evidence kept raw; older evidence offloaded losslessly to retrievable artifacts; clean worker contexts; pending work and side-effect uncertainty; cumulative authorization/consumption; lease ID and next review boundary. Reserve context admission space for output and retain amendments. Progress must never bypass context validity: compact or construct a fresh bounded context, not replay an identical rejected payload. Reopening a task should not silently reset its authorized envelope; after a crash or uncertain tool effect, reconcile before replay. If state persistence is off, say that the task is not durably resumable. Existing optional task state is default-off and new invocations can receive fresh allowance, so this behavior merits an explicit product decision (`packages/teapilot/src/config.ts:200`; `packages/teapilot/src/workspace/task.ts:229–239`; `packages/teapilot/src/host.ts:112–123`).

Finally, run warnings in shadow mode against narrow, no-live-spend replays before allowing a heuristic to interrupt work. Include Mario’s known sequence, productive multi-window work, slow legitimate operations, repeated unchanged failures, changing-but-cosmetic edits, useful new research, stale checks, context admission failure, cancellation, uncertain effects, expired UI delivery, and partial versus accepted outcomes. Measure unnecessary interruptions, missed loops, useful work after warning, correct recovery, cost, and time to human action. Preserve worker-local loop warnings without letting one worker’s churn automatically kill useful parent-task work. This follows the evidence-led evaluation recommendation in the existing research notes, while acknowledging that public examples do not provide benchmarked warning thresholds ([external patterns](../research_notes/Progress%20aware%20task%20supervision/external_patterns.md)).

## Conclusion

The core design decision is not how many more calls to grant; it is what a boundary means. Make it a checkpoint inside an explicit envelope, where the user sees verified progress and can steer before more work proceeds. That turns “continue” from an ambiguous plea after failure into a predictable choice, while preserving hard limits and refusing to call incomplete work done. Implement first as transparent accounting, durable evidence, and shadow-tested warnings; let experience—not arbitrary defaults or optimistic self-reports—determine which leases are useful.
