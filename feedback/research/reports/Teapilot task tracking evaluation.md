# Make Task State Earn Its Claims

Teapilot’s current task tracking is best understood as a durable, evidence-linked work ledger—not a task manager that proves delivery. In this modified checkout, it has meaningful safeguards for persistence, interrupted tool calls, revision conflicts, and evidence retrieval, while leaving decomposition and acceptance largely to the model and user. That balance is useful for agent work, but “done,” a successful request, or a saved Discord app are not equivalent to a verified feature. For the hypothetical `tea-mario` request, the proportionate answer is a short checklist with separate Goomba and Piranha Plant acceptance checks, followed by integration and explicit deployment; a full issue graph or workflow engine is warranted only if actual coordination or recovery needs justify its cost. This is a source review, not an executed benchmark or investigation of an observed Mario incident: no Goomba/Piranha Plant content was found in the repository, and live app state was not inspected.

## Teapilot records progress well, but does not certify completion

The ledger separates several things that are often casually called “task state.” A task has a durable objective and lifecycle; its steps have `ready`, `working`, `blocked`, or `done` status and optional acceptance text. Claims distinguish observed, inferred, and reported basis; evidence references settled tool receipts or saved artifacts. Those schemas are bounded (for example, eight steps and a 6,000-character projection), and updates use revision checks. The tool description is unusually candid: claims and `done` are declarations, not verification. ([`workspace/task.ts`](../packages/teapilot/src/workspace/task.ts#L13-L38); [`agents/task.ts`](../packages/teapilot/src/agents/task.ts#L5-L22))

There are substantive host-owned guarantees behind the ledger: state is scope-bound and validated, snapshots are atomically persisted, evidence is access-checked, and a pending operation left by interruption becomes uncertain and blocks the task rather than being replayed as if known safe. Settled receipts and checked artifacts improve traceability; hashes protect artifact integrity, not truth. Bounded projections intentionally omit older records and provide catalog/artifact retrieval paths, so persistence does not mean every fact is always in the prompt. Nor does a well-preserved transcript guarantee that the next model retrieves the right artifact. ([`workspace/task.ts`](../packages/teapilot/src/workspace/task.ts#L91-L118); [`workspace/task.ts`](../packages/teapilot/src/workspace/task.ts#L162-L227); [`workspace/task.ts`](../packages/teapilot/src/workspace/task.ts#L450-L498))

The key limitation is semantic rather than merely storage-related. A step has no dependency edge, acceptance is descriptive text, and setting `done` does not invoke an evaluator. Execution freshness/check records and unresolved-check tracking are useful warnings, but do not establish that every requested behavior was represented or exercised. Likewise, request success means the host/model completed a response under its execution criteria, not that each user-requested feature passed acceptance; a test failure can appropriately coexist with a successful request if the agent reports the failure honestly. ([`workspace/task.ts`](../packages/teapilot/src/workspace/task.ts#L17-L18); [`agents/run.ts`](../packages/teapilot/src/agents/run.ts#L831-L855))

Think of the ledger as a **job card with attached receipts**, not an independent inspector. The card makes promised work and recorded observations legible; receipts show which operations ran; neither makes a bad result good. A checklist is the plan, a receipt/artifact is evidence, and a playtest is closer to a road test. Keeping these roles separate is a strength of the architecture, provided final reporting does not collapse them into one green “complete.”

## Discord app state is not task state or a recovery checkpoint

The example has an additional operational boundary: implementing a source file and posting/updating an interactive app are different actions. `play_start` posts a new app; `play_update` reloads selected code/assets and can preserve existing live state by default. The update description warns that refreshing source or assets does not replace values already copied into state. Runtime update merges missing top-level initialization fields, not nested arrays; thus adding an enemy to a nested `init().enemies` collection might not populate an already-running app. A newly introduced loop may also need explicit timer startup. These are source-backed hidden dependencies to check, not evidence that either failure occurred in `tea-mario`. ([`agents/play.ts`](../packages/teapilot/src/agents/play.ts#L190-L230); [`discord/play/runtime.ts`](../packages/teapilot/src/discord/play/runtime.ts#L571-L615); [`agents/play.ts`](../packages/teapilot/src/agents/play.ts#L221-L261); [`discord/play/runtime.ts`](../packages/teapilot/src/discord/play/runtime.ts#L311-L315))

Teapilot persists Discord apps separately, including source snapshot, state, timers, status and message identity. A running app can hibernate and wake on interaction; restart behavior is not the same thing as resetting the game or applying pending source edits. `play_inspect`/`play_list` can help locate and inspect an app, but when more than one exists, explicitly selecting its ID is safer than relying on the default newest-running app. `play_test` is a dry-run path, not a Discord post; bounded control probing or simulation is not a full level playthrough. Junior agents can prepare/test yet lack permission to deploy/update, so a junior’s “done” can leave no posted app until an instructor acts. ([`discord/play/store.ts`](../packages/teapilot/src/discord/play/store.ts#L8-L38); [`agents/play.ts`](../packages/teapilot/src/agents/play.ts#L178-L186); [`agents/play.ts`](../packages/teapilot/src/agents/play.ts#L221-L230))

These distinctions are consequential: task status records intention and reported progress; receipts/artifacts preserve observations; conversation history/context helps the next turn remember; execution recovery handles interrupted operations; app storage preserves the game’s live state; and an update deploys new code. None substitutes for all the others. The supplied architecture review traces durable task identity to host execution and notes activation depends on configuration, scratch scope, mode, and tool support. It does **not** establish that a particular Discord `tea-mario` interaction will reopen the same task ledger or replay the right app context. Treat that wiring as uncertain until tested in the intended configuration, rather than inferring it from the existence of persistence code. (See [`workspace/task.ts`](../packages/teapilot/src/workspace/task.ts#L91-L118) and [`agents/play.ts`](../packages/teapilot/src/agents/play.ts#L178-L186).)

## OSS alternatives solve different coordination problems

An OpenCode-style todo is the nearest lightweight analogy: a mutable session progress list makes the next action visible and supports breaking a complex change into chunks. It is cheap and legible, but a todo is not a dependency engine, durable project database, or correctness oracle. ([OpenCode tools documentation](https://opencode.ai/docs/tools/); [OpenCode API specification](https://github.com/anomalyco/opencode/blob/dev/specs/v2/api.html))

Beads is a more appropriate comparison when work needs durable issue identity and dependency readiness across issues or contributors. Its documented `blocks` relations affect what work is ready, and its canonical Dolt database has explicit sync and backup semantics. That capability comes with data lifecycle and coordination concepts to operate; exporting a JSONL file is not the same as canonical storage or backup. For two enemies in one small request, adopting an issue system solely to make a four-item plan would likely add ceremony without proving behavior. ([Beads dependency concepts](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/dependencies.md); [Beads core concepts](https://github.com/gastownhall/beads/blob/main/docs/core-concepts/index.md); [Beads FAQ](https://github.com/gastownhall/beads/blob/main/docs/reference/faq.md))

LangGraph persistence is different again: a checkpointer plus thread identity saves workflow execution state, and an interrupt can pause for a human and later resume. It is useful when a process genuinely needs resumable orchestration or human gates; a checkpoint preserves workflow state, not proof that an external side effect happened exactly once or that code is correct. Wiring a graph runtime just to display task progress confuses execution recovery with work tracking. ([LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence); [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts))

No cited source supplies a controlled head-to-head evaluation, adoption data, failure-rate comparison, or measured cost for these approaches. Avoid declaring a universal winner: session todo fits local visibility, Beads-like issues fit durable coordinated work, and checkpointing fits resumable execution. Teapilot’s ledger adds evidence/recovery semantics beyond a basic list, but still relies on model-authored decomposition and user-meaningful acceptance. These are category comparisons, not drop-in replacement advice.

## Decompose the Mario request around observable behavior

For “implement the Goomba and Piranha Plant into the Super Mario World level 1 port for `discord.play: tea-mario`,” a proportionate task record would have two feature steps and an integration/deployment check. First inspect the explicit app ID, source, current state, controls, existing enemy conventions, timers, and available tests; record the baseline instead of assuming a fresh game. Then implement Goomba in the existing mechanics and test its placement/behavior by an available relevant action path. Implement Piranha Plant with the same attention to shared collision, placement, rendering, and any timer/start behavior actually used in this port. Finally exercise both together in level 1, capture focused assertions and/or gameplay/render evidence, and update the intended live app explicitly—resetting only if fresh initialization is part of the check and acceptable for that game.

Do not invent requirements such as fireballs, multiplayer, or exact fidelity absent user acceptance criteria. Make each step’s acceptance specific after source inspection: the enemy is present at the intended level location, participates in established interaction/collision behavior, and remains correct alongside the other addition. Evidence should include the relevant check/action path and an inspection of the resulting play view where feasible. An edit, `done` label, successful update call, or smoke probe alone is not enough. Failure modes this decomposition exposes include implementing one enemy and forgetting the other, an enemy appearing only in fresh state, an added timer never starting on the live app, an action being skipped by a simulation, or a junior finishing without deployment.

This tracks public advice without treating it as experimental proof. Anthropic recommends the simplest solution that meets the need, legible progress, ground truth from tools, and incremental feature work with concrete test steps in its long-running-agent harness article. The authors describe their own approach and experiments, including cases where unit-level checks missed end-to-end failures; they do not establish that a particular checklist format improves this Teapilot task or game. Their web/browser example must be translated into Discord/gameplay checks, and the cited agent guidance is not a controlled comparison or timeless product mandate. ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents); [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents))

## Improve reporting and continuity before replacing the system

The highest-leverage improvement is disciplined, per-feature reporting: distinguish **implemented**, **checked**, **deployed**, and **remaining/unverified**; attach a short acceptance condition and evidence reference to each feature; identify the exact app ID and whether the check used fresh or existing state. This preserves Teapilot’s lightweight path while making omissions visible. Second, test and document whether the intended Discord configuration actually resumes the same task identity and provides the right tools/context after interruption. Third, add stronger host enforcement only where repeated observed failures justify it—for example, completion gates tied to required acceptance evidence or explicit dependency support. Do not turn task bookkeeping into a success gate that falsely reports overall request failure when the honest outcome is “implemented, but gameplay verification unavailable.”

The useful analogy is a recipe plus a kitchen log: a checklist says what remains, the receipt says what was done, a checkpoint says where a paused cook can resume, and tasting says whether the dish meets the request. Teapilot already has more than a sticky note, but it does not need an external issue database or graph runtime for every small change. Start with the smallest explicit evidence-bearing checklist; graduate to issue dependencies for recurring cross-request coordination, or execution checkpointing for demonstrated interruption/resume requirements. The right system is the least elaborate one that reliably exposes unfinished work and supports a truthful, evidence-based handoff.
