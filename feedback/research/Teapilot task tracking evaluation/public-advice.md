# Public advice on agent task tracking

## What primary agent-engineering advice bears on choosing task-tracking complexity?

### Takeaway
Anthropic recommends starting with the simplest system that meets the need, and making progress legible; for work spanning context windows, it describes feature lists and progress files paired with incremental work. These are published engineering recommendations and reported internal experience, not controlled comparative evidence that a particular tracker causes better outcomes.

### Cited Findings
- Anthropic says to “find the simplest solution possible” and increase complexity only when needed; its post distinguishes fixed-path workflows from agents and says to add complexity only when it demonstrably improves outcomes. [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) (published December 2024; the page currently notes that much of its tooling landscape has changed and points to Managed Agents as the current approach).
- The same post says agent implementations should maintain simplicity, prioritize transparency by explicitly showing planning steps, and carefully craft/document/test the agent-computer interface. It also says agents should obtain ground truth from tool results or code execution to assess progress. [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- Anthropic's long-running-agent article describes a two-part harness: an initializer prepares the environment, feature list, progress log and initial git state; later coding sessions make incremental progress and leave structured updates. The article reports that a feature list helped counter one-shotting and premature completion, and that working on one feature at a time was critical in their experiments. [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- The long-running article's example feature entries include a description and concrete user-observable test steps, with a `passes` flag initially false. It says agents should only change that status, not remove/edit tests, and mark passing only after careful testing. This is the authors' described harness practice, not a universal mandated format. [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Anthropic reports that, in its experiments, agents sometimes changed code and ran unit tests or `curl` yet missed end-to-end failures; explicit browser automation and testing as a human user improved their ability to find/fix bugs. They also note limitations in vision and browser tools. [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- To restart with fresh context, the described coding agent reads progress notes and git history, reads the feature list and selects the highest-priority unfinished feature, starts the app, and verifies a basic end-to-end path before new work. The post says this reduces rediscovery and can reveal existing breakage before extending it. [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- The article explicitly frames multi-context-window consistency as an open problem and its solution as one possible harness; future work includes whether specialized/multi-agent architectures do better and how lessons generalize beyond full-stack web apps. [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

### Inferences
- For the `tea-mario` example (adding Goomba and Piranha Plant to an existing Discord-play game), a short mutable checklist with an explicit playable acceptance check may be more proportionate than a durable issue graph or workflow checkpoint unless work spans sessions, contributors, or recoverable execution boundaries. This is an application of Anthropic's simplicity principle, not a recommendation explicitly tested on teapilot or games.
- Completion should be judged against concrete behavior, not merely a status field: automated tests/build checks can be complemented by a gameplay/Discord interaction that exercises each enemy in level 1. Article's specific browser example is web-app-specific; translate the end-to-end principle to the actual interface.
- For resumed work, a compact progress artifact should record what changed, what remains, the current verification state, and how to run the relevant checks. This follows the described progress-file/restart pattern, but Anthropic does not establish that a particular file format or exact set of fields is optimal.

### Gaps
- These are vendor-published recommendations and reported internal experiments, not a randomized or controlled head-to-head comparison of todo lists, feature JSON, issue trackers, or checkpoints. No effect size, failure-rate comparison, or measured overhead is given.
- The long-running harness article's worked example is a web application using browser automation; applicability and best verification tools for `tea-mario` require repository-specific inspection and testing.
- The “Building effective agents” article is explicitly dated December 2024 in its current caveat and says much of its tooling landscape has changed. Its general simplicity/transparency principles remain stated on the page, but tool-specific details should not be treated as current product guidance.
